# Chapter 2: Worker Node Architecture, `kubelet` & CRI Mechanics

Worker nodes form the execution plane of a Kubernetes cluster, running application containers managed by the control plane.

---

## 1. `kubelet` Internal Architecture & SyncLoop

The `kubelet` is the primary agent running on every worker node. It translates declarative `PodSpec` definitions into physical container execution states on the local host.

```
+-------------------------------------------------------------------+
| kubelet Node Agent                                                |
|                                                                   |
| [ Pod Configuration Sources ]                                     |
|   ├── API Server Watch                                            |
|   ├── Static Pod Manifests (/etc/kubernetes/manifests)            |
|   └── HTTP Spec Endpoints                                         |
|         |                                                         |
|         v                                                         |
| [ PodManager ] <------- Event Notifications ------+               |
|         |                                         |               |
|         v                                         |               |
| [ SyncLoop ] <--------------------+               |               |
|   ├── configCh (PodSpec updates)  |               |               |
|   ├── plegCh (Lifecycle events) --+               |               |
|   ├── syncCh (Periodic ticker)                    |               |
|   └── probeCh (Liveness / Readiness health)       |               |
|         |                                         |               |
|         v                                         |               |
| [ Pod Workers ] (One goroutine per Pod)           |               |
|         |                                         |               |
|         v gRPC over Domain Socket                 |               |
| [ CRI Client ] -----------------------------------+               |
+-------------------------------------------------------------------+
            |
            v gRPC
+-------------------------------------------------------------------+
| containerd Daemon (CRI Runtime)                                   |
+-------------------------------------------------------------------+
```

### 1.1 The `SyncLoop` Channels
The core driver of `kubelet` is an event loop consuming 4 primary Go channels:
1. **`configCh`:** Receives PodSpec additions, updates, and deletions from config sources.
2. **`plegCh`:** Receives pod lifecycle events generated by PLEG.
3. **`syncCh`:** Ticker channel triggering periodic re-synchronization (default every 1 sec) for pods needing state alignment.
4. **`livenessCh` / `readinessCh`:** Consumes output from probe execution workers.

### 1.2 PLEG (Pod Lifecycle Event Generator)
Older versions of `kubelet` polled container runtimes continuously for status updates, causing massive CPU overhead.
* **PLEG Mechanism:** PLEG periodically queries the CRI runtime for runtime container states, compares them against previous snapshots, and converts state changes into explicit events (`ContainerStarted`, `ContainerDied`, `ContainerChanged`).
* **Relisting Overhead:** If PLEG relisting exceeds 3 minutes, the node transitions to `NotReady` with a `PLEG is not healthy` status.

## 2. Container Runtime Interface (CRI)

The **CRI** is a standardized gRPC interface decoupling `kubelet` from specific container runtime implementations.

```
+------------------+                    +-------------------------+
| kubelet          | -- gRPC Socket --> | containerd / CRI-O      |
| (CRI Client)     | (/var/run/...)     | (CRI Server Daemon)     |
+------------------+                    +-------------------------+
```

### 2.1 Core CRI gRPC Services
The CRI protocol splits responsibilities into two distinct gRPC service specifications:

#### 1. `RuntimeService` (Container & Pod Sandbox Management)
* `RunPodSandbox(config)`: Creates the network namespace, pause container, and cgroup parent for a Pod.
* `StopPodSandbox(podSandboxID)` / `RemovePodSandbox(podSandboxID)`: Tears down pod infrastructure.
* `CreateContainer(podSandboxID, config, sandboxConfig)`: Creates application container inside the pod sandbox.
* `StartContainer(containerID)` / `StopContainer(containerID, timeout)`: Manages execution states.
* `ExecSync(containerID, cmd)`: Runs one-off diagnostic commands inside containers.

#### 2. `ImageService` (Container Image Management)
* `PullImage(image, auth)`: Pulls container image layers from remote registries.
* `ListImages()` / `RemoveImage(image)`: Manages local image storage cache.

## 3. Container Execution: `containerd` & `runc`

When `kubelet` issues a `RunPodSandbox` or `CreateContainer` CRI call, `containerd` delegates low-level execution to `runc` via `containerd-shim`.

```
kubelet (CRI Client)
       |
       v gRPC
containerd daemon
       |
       v
containerd-shim-runc-v2 (Per Pod / Container)
       |
       v Exec (runc creates namespaces/cgroups, then exits)
[ runc ]
       |
       v
[ Application Container Process ] (Adopted by containerd-shim as PID 1 parent)
```

### 3.1 Role of `containerd-shim`
Why does Kubernetes use a shim process for every container?
1. **Daemonless Containers:** Allows `containerd` daemon to be restarted or upgraded without stopping running application containers.
2. **IO Stream Maintenance:** Keeps standard I/O streams (`stdin`, `stdout`, `stderr`) and file descriptors open even if `containerd` crashes.
3. **Exit Status Collection:** Waits for container process termination and captures the exit code for `kubelet`.

## 4. `kube-proxy` & Service Abstraction

`kube-proxy` runs on every worker node, listening to `kube-apiserver` for Service and Endpoints object updates to direct traffic destined for Virtual IPs (`ClusterIP`).

### 4.1 Execution Modes
1. **`iptables` Mode (Default):**
   * Writes sequential `PREROUTING` and `KUBE-SERVICES` `iptables` rules.
   * Uses random probability matching (`-m statistic --mode random`) to load balance across Pod IPs.
   * **Limitation:** $O(N)$ lookup complexity. Scale degrades when rules exceed ~20,000.
2. **`IPVS` Mode:**
   * Uses Linux IP Virtual Server (IPVS) kernel hash tables ($O(1)$ complexity).
   * Supports advanced load balancing algorithms (Round Robin, Least Connection, Destination Hashing).
3. **eBPF Mode (Cilium Bypass):**
   * Replaces `kube-proxy` completely with eBPF programs attached to socket layer (`sock_ops`), bypassing netfilter overhead entirely.

## 5. Staff Engineer Node Operational Checklist
1. **PLEG Latency Monitoring:** Monitor `kubelet_pleg_relist_duration_seconds`. Spikes indicate slow container runtime responses or unresponsive storage mounts.
2. **`crictl` Diagnostic CLI:** Use `crictl` (CRI CLI tool) directly on worker nodes to debug container runtimes bypassing `kubelet`:
   * `crictl pods` — List active Pod sandboxes.
   * `crictl ps` — List running CRI containers.
   * `crictl logs <container-id>` — Inspect raw container runtime logs.
3. **Containerd Storage Cleanup:** Configure `imageGCHighThresholdPercent` (e.g., 80%) in `kubelet` config to automatically trigger image garbage collection when node disk space drops.
