# Chapter 4: Merging, Rebasing & Conflict Resolution — Deep Dive Notes

> **Core Theme:** Combining histories in the DAG. Comparing **3-Way Merges**, **Lowest Common Ancestor (LCA)**, **Rebase Commit Replaying**, `cherry-pick`, and `revert`.

---

## 1. 3-Way Merge & Lowest Common Ancestor (LCA)

When you run `git merge feature` into `main`:

```
          [ Commit C1 ] (Lowest Common Ancestor - LCA / Merge Base)
             /       \
     [ Commit C2 ]   [ Commit C3 ]
     (main branch)   (feature branch)
             \       /
          [ Commit C4 ] (3-Way Merge Commit with 2 Parents)
```

### The 3-Way Merge Calculation:
Git compares three trees:
1. **LCA (Merge Base):** The common ancestor commit where branches diverged (`git merge-base main feature`).
2. **Ours (`main`):** Current branch `HEAD` tree.
3. **Theirs (`feature`):** Incoming branch tree.

- **Automatic Merge:** If `feature` modified a line that `main` did not touch since LCA, Git automatically applies `feature`'s change.
- **Merge Conflict:** If both `main` and `feature` modified the **exact same lines** differently since LCA, Git stops and injects conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`).

---

## 2. Fast-Forward vs. Non-Fast-Forward (`--no-ff`)

- **Fast-Forward Merge:** If `main` has zero new commits since `feature` branched off, merging simply moves `main`'s pointer forward to `feature`'s latest commit. No new commit object is created!
- **Non-Fast-Forward (`git merge --no-ff`):** Explicitly creates a **Merge Commit** with 2 parent pointers, preserving visual feature branch topology in DAG visualization logs.

---

## 3. `git rebase` Internals: Replaying Commits

Rebasing rewrites commit history to create a linear DAG topology.

```
BEFORE REBASE:
C1 ──► C2 (main)
 └──► C3 ──► C4 (feature)

AFTER `git rebase main` ON FEATURE BRANCH:
C1 ──► C2 (main) ──► C3' ──► C4' (feature - New Commit SHAs!)
```

### How `git rebase` Executes Under the Hood:
1. Finds LCA of `feature` and `main`.
2. Temporarily stores diffs of `C3` and `C4` in temporary patch files.
3. Resets `feature` branch pointer to `C2` (`main` `HEAD`).
4. Re-applies patch `C3` onto `C2` $\to$ Creates **NEW commit `C3'`** (with different SHA-1 hash!).
5. Re-applies patch `C4` onto `C3'` $\to$ Creates **NEW commit `C4'`**.

> **Golden Rule of Rebasing:** NEVER rebase commits that have been pushed to a shared remote repository! Rebasing changes commit SHAs, causing severe history divergence for teammates.

---

## 4. `git cherry-pick` vs. `git revert`

- **`git cherry-pick <commit_sha>`:** Extracts the patch diff generated by `<commit_sha>` and applies it onto current `HEAD` as a brand new commit.
- **`git revert <commit_sha>`:** Calculates the **inverse diff** of `<commit_sha>` and creates a new commit that safely undoes those changes without deleting historical commits from the DAG log.
